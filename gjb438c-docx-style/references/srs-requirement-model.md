# SRS 需求编写与内容模型

## 先识别来源和验收边界

适用于附录J的编写、内容迁移与评审。标准逐项依据在[附录J矩阵](srs-appendix-j.md)，本文的记录字段及JSON组织主要为`增强`实现策略。标准允许表格、条内注释及其他等效形式，不限定JSON或每条需求表格长相。

把来源内容分为软件行为/能力、接口、数据、性能/质量/Security/Safety/环境/资源/约束、项目过程、背景说明、待定事项。项目配员、开发过程、供应商承诺和实施活动不能自动转成软件行为；人员容量、内置训练、软件保障和交付包装若构成CSCI验收约束，仍可属于J3.13–3.16。

建立**独立的来源需求台账**，从合同、系统/子系统规格说明、分配决定、批准变更等逐项取得。先确认哪些已分配给当前CSCI，再映射到SRS或IRS。禁止从已经生成的SRS需求反向拼出“完整来源台账”，那样不能发现遗漏来源。

## 正式需求记录

正式需求必须有项目唯一标识，并能定义具体检验对象、合格性方法及系统/子系统追踪。保留已有受控编号，例如`REQ_17`、`R-控制-004`均不因缺少`SRS-`前缀而不合格。技术上的唯一性检查不能证明跨版本稳定性，重命名需保存对应关系。

编写时按下列内容核查，避免把适用字段误当全部需求的无条件必填项：

| 内容 | 使用条件与判定 |
|---|---|
| 名称、主体、主要义务 | 使用清晰规范性语言，优先用“应”；既有等效义务表述可保留。含“应”不代表可验证。 |
| 状态/方式、角色、触发和前置条件 | 对验收结果有影响时明确；多个需求共享的状态可按组关联。 |
| 输入、来源、处理、输出或后置状态 | 适用于相应能力、接口和数据需求；设计或硬件约束不必虚构输入输出。 |
| 性能、精度、容量、时序、连续性、允许偏差 | 使用来源确定的对象、单位、负载和条件；不能用“快速/高效”代替边界。 |
| 异常、未授权、越界、错误、恢复 | 按能力/接口及风险适用性明确；不适用要能说明，未知需TBD。 |
| 优先顺序、关键性 | 可在3.18统一声明全部同权；若项目规定差异排序则给受控排序/权重和关键性；未规定或明确不适用时如实说明，不把全部缺省当成标准强制错误。不能用同权声明抹去已知的Safety/Security特殊处理要求。 |
| 合格性方法 | 对应实际义务，允许一种或多种；基础方法与受控扩展见下文。 |
| 来源或派生依据 | 已分配系统/子系统需求，或产生需求的系统实现一般需求/设计决定。合同、法规、批准变更等还须说明如何形成当前分配依据。 |
| 证据计划及通过判据 | 评审增强：说明准备如何判断和留证；计划不能写成已经测试、已通过、已认证。 |

不同条件、独立可判定动作、不同输出或不同方法常提示需要拆分。构成同一不可分事务的协调步骤可保留在一条，由一个明确判据整体判定。不机械地按“和/及”拆句。配置项、数据元素或段落的编号也不自动等于正式需求编号。

3.1的状态/方式说明可为背景记录；若状态转换、切换限制或特定状态行为本身是验收义务，作为正式需求放入统一记录和覆盖检查，不能仅放在状态表而漏掉ID、合格性与追踪。

## schema 2.0 结构及关联

机器接口以[srs-content-schema.json](srs-content-schema.json)及[共享校验模块](../scripts/srs_model.py)的实际校验为准。`schema_version`为`2.0`。无版本旧模型可进入兼容规范化；规范化只能转换已存在字段，不能补写来源、验收阈值、负责人、批准或裁剪结论。

| 对象/字段 | 用途及关联 |
|---|---|
| `metadata`、`references` | CSCI与文档元数据、受控引用文档。引用登记保存编号、标题、编写单位、修订版、日期；不能正常获取时给获取来源。机器字段不是发布本机绝对路径的理由。 |
| `source_requirements` | 独立来源台账。`id`、`statement`标识原需求；`reference_id`及`location`指其受控文档和条款；`allocation`记录`allocated`或`not_allocated`；`disposition`记录`implemented`、`deferred`或`not_applicable`，需要理由时使用`reason`。处置标签本身不是项目批准。 |
| `requirements` | 正式需求的`id`、`clause`、`statement`为基本标识/定位/内容；`clause`支持3.1以及适用的第3章需求条款。`input`、`output`、`boundary`、`exception`等按适用性编写；字段缺省不等于内容必然充分。 |
| `source_ids`或`derivation` | `source_ids`关联来源台账ID；派生项以`derivation.basis`和`derivation.rationale`说明产生依据与理由，不伪造上层ID。 |
| `states`、`capabilities`、`interfaces`、`data` | 分别登记状态、能力、接口、数据；需求用`state_ids`、`capability_id`、`interface_id`、`data_ids`引用相关对象。未知关联不能留成看似有效的编号。 |
| `interface_diagram` | 可用图文件的`path`和`description`，或`reference_id`、`location`定位受控图；纯文字说明不能证明已经提供了可视接口图。输入图路径用于装配，不作为交付正文中的来源引用。 |
| `notes` | 帮助理解正文的背景、术语、缩略语和公式说明，对应第6章；不隐藏新的验收义务。 |
| `priority_policy` | `mode='equal'`且`statement`明确说明全局同优先级/关键性，可避免逐条重复；`mode='ranked'`时说明项目的不同优先/关键性安排；3.18明确不适用时通过裁剪记录说明。不能将缺数据自动推成同权。 |
| `qualification` | 以`requirement_id`关联，记录方法、条件、计划证据、通过判据；与需求记录里的`qualification_methods`一致。 |
| `forwardTrace`、`reverseTrace` | 正向表达来源到需求，反向表达需求到来源/派生依据；结构见schema。双向表存在不代表关系正确，需与独立来源台账和正文核查。 |
| `external_target` | 在正向/反向追踪或合格性记录中，与本地`requirement_id`二选一；以`reference_id`、`requirement_id`、`location`定位IRS需求。其文档须出现在受控引用及接口IRS登记中。 |
| `tailoring` | 每项`clause`、`status`（`applicable`、`not_applicable`、`tbd`）、`reason`、`basis`；不适用/裁剪需具体理由和依据，最高裁剪节点可覆盖整个子树。 |
| `tbd` | 保存`id`、`issue`、`impact`、`owner`、`closure_condition`、`status`和`affected_ids`；未决文字需与实际TBD ID关联，不能到处写无法闭合的“待定”。 |
| `qualification_method_extensions` | 每项`name`、`definition`、`approval`，供项目受控扩展使用。未知方法值与已登记的受控扩展不同，不能静默接受拼写错误。 |

草稿缺失的事实显示为未提供或受控待定；不会由工具自动变成批准裁剪或完整来源。字段可解析只说明语法/关联成立，语义真伪仍需核对来源。

## 递归能力与写作配置

默认`training-review`，显式`gjb-standard`仅采用标准内容检查；两者均独立选择draft/review。新增父子树排序、研制状态、图类型/覆盖、物理章节和合同映射字段见[培训配置及公共接口](srs-training-review.md)。`clause=3.2`表示标准类别，实际章节由能力树生成，不用章节迁移改变正式需求ID。旧schema 2.0无需升级版本；旧字段继续有效，培训配置新增缺口在draft报告，不自动补事实。

## 接口、内部数据和 IRS

接口清单用项目唯一ID标识双方、方向和接口状态。每个接口独立组织需求及数据，不把所有接口的需求铺到同一个占位小节。双方不同大小、速率、格式等期望值要显式协调或关联TBD。

- `definition='inline'`：在当前SRS描述接口；按附录J3.3.X(a–g)逐项判断适用性。不要把鉴权、重试、幂等、网络会话等无条件强加到普通文件或人工接口。
- `definition='irs_reference'`：以`irs_reference.reference_id`指向`references[].number`，用`irs_reference.location`定位受控IRS中的接口/图/需求。不能只写“见IRS”或未经验证的文件名。
- 内部接口已有验收约束时按J3.3描述；内部数据已有约束时按J3.3.X(c)、(d)描述数据库、数据文件、元素与组合体。全部留待设计时如实说明，不编造接口细节。
- 外部实体行为写成假设、触发条件或依赖，CSCI自身响应才是本SRS的义务。依赖未落实时不得宣称实际连通或已满足外部服务条件。

标准J5(b)允许追踪至受控IRS中的CSCI需求。评审必须能定位其文档号、版次、条款/需求标识及相应分配来源；不能因为本SRS没有复制IRS全文就认定遗漏。模型以`external_target`表达这种外部目标，关联受控引用及接口IRS登记；正文和人工审核继续核实外部需求真实存在及适用版次，不能伪造本地需求ID骗过校验。

## 引用文档与内部引用

引用登记中的编号、标题、编写单位、修订版、日期以原文为准；仅当不能正常获取时要求获取来源。是否采用未注日期文档的最新版属于项目版次控制决定，不是J2自动赋予的规则。未知信息须关联TBD，不能从记忆标准化标题或日期。

正文以受控文档号及条款/图/表位置引用来源。区分产生需求的规范性引用与提供背景的资料性引用。DOCX内部章节、图表、附录和需求引用宜使用书签/交叉引用，这是可维护性增强；应检查它实际指向的对象，不能只检查域或书签存在。

## 合格性与追踪闭合

基础方法受控值为`演示`、`测试`、`分析`、`审查`、`特殊合格性方法`；最后一个是标准“特殊的合格性检验方法”的模型简名。标准用“可以包括”，不是封闭枚举；扩展须登记名称、定义和项目控制依据。

逐条检查：来源台账全部已分配项有实际去向；SRS正式需求有来源/派生依据；目标需求存在且条件与来源一致；方法能判断该义务；计划证据与通过判据具体；多对多映射不隐藏被漏掉的子义务。`deferred`、`not_applicable`只有标签不代表闭合，须核验其理由、依据和对交付基线的影响。

TBD由“待定事实→影响对象→责任归属→闭合条件→证据/状态”串联。已解决状态必须能指出解决依据，并同步更新正文和关联表。没有责任信息时可在draft明确未知，不得发明联系人或随意承诺关闭日期。

## 草稿与评审使用方式

`--mode draft`为默认：保留资料缺口和TBD，输出可继续完善的草稿；资料/证据不足通常作为warning，重复ID、错误类型、已建台账中的失效引用、未知方法等确定性缺陷仍是error。旧模型缺整个来源台账属于资料缺口，不能当作来源已核验。

`--mode review`加强资料完整性、合格性、引用、分配覆盖、裁剪和TBD闭合检查。审计器的`--strict-srs`保留为兼容的严格审核入口。严格模式不代表工具执行了人工语义或视觉检查。

审计器以`--content-json content.json`接收独立模型；生成器不将模型嵌入DOCX。核对模型与DOCX为同一交付版本，不能用无关模型补足另一个文档的检查。`--template-profile auto|standard|SRS-P09`区分自动识别、标准内容检查和特定模板检查，不对合规的其他项目模板强制三分节。

低层`sections`仅允许draft装配，review生成要求规范模型，不能用低层输入绕过校验。低层内容未提供独立来源和结构化关联时，只能据实际可检查范围报告，不能因DOCX成功生成或结构通过而声称需求闭合。[评审门禁](srs-review-gate.md)定义机器、语义、视觉三类检查的状态与交付口径。
